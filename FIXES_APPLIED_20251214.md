# System Fixes Applied - December 14, 2025

## Executive Summary

Applied **4 critical fixes** to address systematic failures in query orchestration identified from evaluation results (Q1-Q12 baseline run). The system was in "degraded mode" - accepting queries but producing ungrounded responses with missing SQL execution and fallback sample data.

---

## Issues Identified (from Evaluation Analysis)

### Root Cause: Broken State Contract
- **Q1, Q2, Q8, Q9**: Returned "internal error" with no SQL generated  
- **Q3-Q7, Q10-Q12**: Executed empty SQL strings (`sql_executed: [""]`) while returning sample customer data
- **AnswerAgent behavior**: Producing ungrounded responses ("The query executed does not provide information about suppliers...") instead of failing

### Three-Part Failure Mode
1. **SQL not propagated** from generation (JoinPlanAndSQLAgent) → execution (ExecAndRecoveryAgent)
2. **Fallback "sample queries"** being executed when SQL is empty/missing  
3. **AnswerAgent allowed to finalize ungrounded data** instead of routing to error handling

---

## Fixes Applied

### **Fix 1: Hard Block on Empty SQL Execution**
**File**: `langgraph_integration/agents/exec_recovery/agent.py` (lines 219-246)

**Problem**: When `sql_query` was empty/missing, the executor would proceed silently or call MCP with empty string, triggering fallback sample data.

**Solution**:
- Changed from silent error handling to **hard fail** when `sql_query` is empty
- Return `exec_result` with `ok=False` and error info immediately
- Error message: "No valid SQL query was generated by the planning agent"

**Impact**: Prevents silent fallback to sample queries; surfaces SQL generation failures immediately.

```python
if not sql or not sql.strip():
    error = {
        "type": "NO_SQL_GENERATED",
        "message": "No valid SQL query was generated...",
    }
    logger.error(f"❌ HARD FAIL: {error['message']}")
    state["error_info"] = error
    state["exec_result"] = {"ok": False, "data": [], "error": error["message"]}
    return state
```

---

### **Fix 2: Grounding Gate Before AnswerAgent**  
**File**: `langgraph_integration/orchestrator.py` (lines 1386-1418)

**Problem**: AnswerAgent was formatting and returning responses even when underlying SQL execution failed or produced irrelevant data, creating "explanations" for ungrounded results.

**Solution**:
- Added explicit grounding validation gate for data queries  
- Checks: `exec_ok=True` AND `sql_query` present AND no exec_error
- If gate fails → return structured error instead of ungrounded response

**Impact**: Prevents responses like "The query executed does not provide information about suppliers" when supplier query wasn't actually executed.

```python
if is_data_query:
    # Hard gate: if no successful SQL execution for a data query, fail
    if not exec_ok or not sql_query or exec_error:
        logger.warning(f"⚠️  GROUNDING GATE ACTIVATED")
        state["error_info"] = {
            "type": "UNGROUNDED_RESPONSE_PREVENTED",
            "message": "Cannot answer this query..."
        }
        state["final_response"] = "I wasn't able to retrieve the information..."
        return state
```

---

### **Fix 3: Updated Evaluation Success Criteria**  
**File**: `eval/run_benchmark.py` (lines 52-109)

**Problem**: `artifact_validation_errors()` had weak success criteria. Evaluation was counting "completed HTTP request" as success even with no SQL execution, no tables used, or grounding gate activated.

**Solution**:
- Added explicit checks for all failure conditions:
  1. Error phrases in response (e.g., "wasn't able to retrieve", "too vague")
  2. Empty SQL execution (no non-empty strings in `sql_executed`)
  3. No tables used (indicates discovery failure or sample data fallback)
  4. No results returned (no `row_count` and no `result_preview`)
  5. Grounding gate activation (error_type contains "UNGROUNDED" or "NO_SQL")

**Impact**: 
- Run summary will now correctly report failed queries  
- Previously "100% success" runs will show actual failure counts
- Enables proper analysis of system reliability

---

### **Fix 4: Enforce SQL State Contract** (Implicit)  
**Mechanism**: Fixes 1 and 2 together enforce that:
- SQL generation MUST produce non-empty `state["sql_query"]`
- Execution node MUST receive valid SQL before attempting MCP call
- Answer agent MUST gate on successful execution before responding

**Impact**: 
- Prevents SQL loss between nodes
- Breaks silent fallback chains
- Creates clear failure points for debugging
